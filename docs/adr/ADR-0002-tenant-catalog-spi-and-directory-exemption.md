# ADR-0002：TenantCatalog SPI 与租户目录表豁免纪律

| | |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-10-15 |
| 关联 | 设计文档 §6.1（core / TenantCatalog）、§2（痛点 2 的目录表教训）、§14 R1-P0③ |

## 背景（Context）

TenantKit 的批量能力（`Tenants.forEach` 遍历全部租户执行任务）与供给能力
（provisioning）都需要一份「当前活跃租户清单」。但 tenantkit-core 是纯库：它既不绑定
数据库，也无法凭空枚举租户——清单只存在于各业务系统里（配置文件、租户目录表、
组织服务）。没有清单来源，forEach 就是空转，provisioning 无从下手（评审 R1-P0 指出，
这是能力成立的前置条件，不是可选件）。

生产线上同时暴露了第二个问题：真实系统里的租户目录/组织表，靠**业务代码注释**口头
豁免租户过滤（「本表全局共享，勿加 tenant 过滤」之类）。手写过滤的年代这勉强可用；
一旦 v1.x 引入行级拦截器做默认全表过滤，目录表查询会被自己的过滤器拦住——批量任务
查不到租户清单，或触发递归解析，是可预见的生产事故。这条教训必须在 v0.1 就写成
纪律，而不是等 v1.x 实现时再补。

## 决策（Decision）

1. **定义最小 SPI，core 不内置 DB 实现**：

   ```java
   /** 租户清单来源 SPI（R1-P0：core 无法凭空枚举租户）。 */
   public interface TenantCatalog {
       List<TenantId> activeTenants();
   }
   ```

   清单来源由用户接入；core 只消费，不猜测。

2. **v0.1 内置 config 清单实现**：`tenantkit.tenants: [alpha, beta]`，覆盖开发与
   小规模场景；DB 查询实现交用户接，文档示例翻拍生产 OrganizationService 模式。

3. **目录表豁免纪律写入文档，为 v1.x 行级拦截器立规矩**：**租户目录表本身必须列入
   任何行级过滤器的豁免名单**。这条生产教训从今天起是文档强制项。同理，kit 自己的
   供给账本表（`tenantkit_seed_history`）也是全局表，必须进未来行级过滤器的豁免名单。

## 后果（Consequences）

- 用户必须提供至少一种清单来源；既未配置 `tenantkit.tenants` 也未实现 SPI 时，
  相关能力**显式失败**（fail-fast），绝不静默返回空清单——空清单会让 forEach 与
  provisioning 「看起来正常地什么都没做」，正是本库处处设防的那类静默失败。
- SPI 面保持最小（一个方法）：缓存、分页、启停语义由用户实现决定，kit 不越权，
  也不为 DB 实现定义中介抽象。
- v1.x 行级拦截器的设计文档必须把「目录表/账本表豁免」列为强制检查项，本 ADR 是其
  依据；示例应用与文档示例从 v0.1 起即按此纪律书写，形成一致叙事。
